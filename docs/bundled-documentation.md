# Bundled documentation maintenance

The CLI embeds a pinned developer-site snapshot for `thruput docs`.
Ordinary source builds use the checked-in snapshot; they do not require a
`developers-site` checkout. The procedure below is for maintainers selecting a
new snapshot.

1. In `developers-site`, build the selected clean commit with
   `pnpm package:snapshot`, or download `docs-snapshot-<commit>` from its successful
   CI run. It contains `snapshot.tar.gz` and `snapshot-lock.json`.
2. Run `python3 scripts/import-docs-snapshot.py /path/to/artifact` here. This
   validates the archive's checksum, size, clean source identity and contents,
   removes historical skill downloads (`agent-guide.md` and `agents/`), then
   writes the documentation archive and its updated pin to
   `crates/cli/assets/docs/`. The pin retains the original archive checksum in
   `sourceArchiveSha256`; the documentation source identity is unchanged.
3. Review the source revision, documentation/version notes, and archive pin;
   commit both files with the CLI change. Never select the latest docs implicitly.
4. Run the snapshot checks and CLI tests. Normal CLI packaging embeds those exact
   bytes, so consumers need no build-time docs checkout or separate access token.

`python3 scripts/import-docs-snapshot.py` without an argument verifies the current
pin. The Rust bundle test checks the same pin/content contract and cache recovery.
The full documentation set can evolve independently of CLI releases; changing
what a CLI ships is an explicit selection. A guide version in the manifest does
not assert that every SDK example or deployed Devnet matches that version.

## Markdown snapshot contract

The CLI consumes Markdown generated by the developer-site build. A compatible
snapshot contains `markdown/index.md` and a self-contained `markdown/` tree:
individual pages, section bundles, and a full bundle. Relative links and local
assets must resolve within this tree when it is copied away from the server.
Pages should retain their hosted source URL and documentation version context.
The snapshot's existing `snapshot.json` supplies the source revision.

`thruput docs` reports the Markdown index when present.
`thruput docs export --output <new-directory>` copies that tree and adds
`snapshot.json` at the export root. Reserve this filename for snapshot identity.
Older snapshots remain valid for browser serving but cannot be exported as a
Markdown set. Do not derive Markdown from their generated HTML in the CLI.

The site build generates and checks these files together with the HTML. Its
Markdown manifest records the same source identity as `snapshot.json`; both
the importer and the CLI verify that they match. Keep the Markdown tree and
the browser site in the same selected archive.

External `--dir` snapshots with Markdown must also include a valid
`markdown/manifest.json` with schema version 1 and the exact root snapshot
identity. Serving or exporting rejects missing, malformed, or mismatched
manifests before reporting or copying the documentation.

## Background service state

The background server records its authenticated control identity in private,
atomically written `state.json` and `state.backup.json` files under the
`thruput/docs-service` cache directory. Status, start, and stop can restore a
missing or invalid primary file from the validated backup. The normal instance
identity check still runs before reuse or stop; a reused port is not ownership.

If neither copy is valid, the command reports an error and preserves both files.
Restore a trusted copy to recover control. Do not assume the server stopped or
kill a process based only on a port number. A successful stop removes both copies
and keeps the extracted documentation.
